# YouTube 4K 다운로더 — 개발 계획 초안

- 문서 상태: **초안 (v0.1)**
- 작성일: 2026-09-13
- 대상 산출물: Windows / macOS / Linux 데스크톱 다운로더

---

## 1. 목표

한 문장: **URL을 붙여넣으면 4K(2160p) 영상을 오디오와 함께 하나의 파일로 저장해 주는 도구.**

| 구분 | 목표치 |
| --- | --- |
| 최대 화질 | 2160p(4K), 가능하면 4320p(8K)까지 동일 로직으로 확장 |
| 프레임레이트 | 60fps 지원 |
| HDR | HDR 스트림 감지 및 선택 가능(변환은 하지 않고 원본 유지) |
| 다운로드 속도 | 병렬 fragment 다운로드로 단일 연결 대비 3배 이상 |
| 동시 작업 | 기본 3개 큐 동시 처리 |
| 조작 | URL 붙여넣기 → 클릭 1~2번으로 완료 |

### 비목표 (명시적으로 하지 않는 것)

- DRM 우회, 유료/멤버십 전용 콘텐츠의 권한 우회
- 로그인 자격증명을 서버로 전송하는 기능 (쿠키는 **로컬에서만** 사용)
- 대량 자동 수집(크롤링)·재배포용 기능

## 2. 핵심 기술 배경 — "왜 4K는 그냥 안 받아지나"

YouTube는 화질별로 스트림을 이렇게 제공합니다.

| 구분 | 코덱 | 최대 화질 | 오디오 포함 |
| --- | --- | --- | --- |
| Progressive (`format 18`, `22`) | H.264 + AAC | **720p** (22번이 최대 1080p, 대부분 비활성) | O |
| DASH video-only | VP9 / AV1 / H.264 | **4320p** | X |
| DASH audio-only | Opus / AAC | — | O |

즉 **1080p를 넘는 순간 오디오가 붙어 있는 단일 스트림은 존재하지 않습니다.**
따라서 파이프라인은 반드시 다음 3단계가 됩니다.

```
1) 포맷 목록 추출  →  2) 영상/음성 스트림 각각 다운로드  →  3) ffmpeg으로 병합(remux)
```

병합은 **재인코딩 없이 컨테이너만 교체(remux)** 합니다. 재인코딩은 화질 손실 + 수십 배 느림.

### 코덱 선택 정책 (기본값)

| 우선순위 | 코덱 | 이유 |
| --- | --- | --- |
| 1 | **VP9** | 4K 지원 + 하드웨어 디코딩 보급률 높음, 호환성 무난 |
| 2 | AV1 | 용량 이득이 크지만 구형 기기 재생 부담 → "용량 우선" 옵션에서 선택 |
| 3 | H.264(avc1) | YouTube에서 보통 1080p까지만 제공 → 4K에는 사용 불가, 호환성 모드용 |

컨테이너는 **MP4 우선, VP9/Opus 조합이면 MKV**로 자동 결정(옵션으로 강제 MP4 + AAC 변환 허용).

## 3. 기술 스택 (결정안)

| 레이어 | 선택 | 대안 | 선택 이유 |
| --- | --- | --- | --- |
| 언어 | **Python 3.11+** | Node/Go/Rust | yt-dlp를 라이브러리로 직접 임베드 가능. 포맷 파싱 로직을 직접 만들 필요 없음 |
| 추출 엔진 | **yt-dlp (라이브러리 임포트)** | 서브프로세스 호출 | 진행률·에러를 구조화된 훅으로 수신 |
| 병합/변환 | **ffmpeg (번들)** | 시스템 설치 요구 | 사용자 설치 단계 제거 |
| GUI | **PySide6 (Qt6)** | Tauri, Electron | Python 코어와 같은 프로세스, 네이티브 룩, 배포 용량 무난 |
| 패키징 | PyInstaller (+ NSIS / dmg) | Briefcase | 실사용 사례·자료 풍부 |
| 테스트 | pytest + pytest-asyncio | — | |

> **결정 필요 지점**: GUI를 PySide6(Qt)로 갈지, 웹 기술(Tauri)로 갈지는 M3 진입 전에 확정.
> 이 계획서는 PySide6를 기본안으로 잡고 작성했습니다.

## 7. 구현하며 바뀐 결정

계획서를 그대로 따르지 않은 지점과 그 이유:

| 계획 | 실제 | 이유 |
| --- | --- | --- |
| "MP4 강제 시 opus → AAC 재인코딩" | **재인코딩 안 함.** mp4 강제 시 AAC 오디오와 mp4 친화 영상 코덱을 *선택* | YouTube 는 어차피 AAC 트랙을 함께 주므로 재인코딩할 이유가 없다. 유일한 손실 지점이 사라졌다 |
| 병합을 직접 구현 | yt-dlp 에 위임, `merger.py` 는 탐색·검증 담당 | 검증된 경로를 다시 만들 이유가 없다. 대신 '소리 없는 4K 파일' 을 잡는 결과 검증을 추가 |
| HDR 은 옵션으로 우대 | **양방향 선호** — 요청 안 하면 SDR 우대 | HDR 스트림이 비트레이트가 높아 가만히 두면 자동 선택된다. SDR 화면에서 색이 바래 보인다 (테스트가 잡아냄) |
| 연령 제한 오류는 안내만 하면 됨 | **화면에 로그인 브라우저 선택을 추가** | GUI 에서 "쿠키를 연결하세요" 라고만 하면 손쓸 방법이 없는 막다른 길이 된다 |
| 오류는 추출 실패로 일괄 처리 | 네트워크 오류를 별도 분리 | 연결 실패를 "YouTube 사양 변경" 으로 안내하면 사용자가 엉뚱한 곳을 고친다 (실행 중 발견) |
| ffmpeg 은 받아서 넣으면 끝 | **왕복 먹싱·디먹싱 검사**를 거쳐야 채택 | PyPI 경유 static 빌드 7.0.2 가 MPEG-TS 입력에서 세그폴트했다. 먹싱은 멀쩡해서 `-version` 확인만으로는 안 드러난다 (아래 참고) |

### 플랫폼 차이는 CI 에서 잡는다

초기에는 CI 가 Ubuntu 만 돌렸고, 그 결과 윈도우 전용 문제 여섯 가지가 릴리스
빌드 단계에 가서야 드러났다. 지금은 CI 매트릭스에 windows-latest 를 넣었다.

| 문제 | 성격 |
| --- | --- |
| 경로 구분자를 `/` 로 가정한 단언 | 테스트 |
| 확장자 없는 `ffmpeg` 파일로 탐색 시험 | 테스트 (윈도우는 `.exe` 를 찾는 게 맞다) |
| 셸 스크립트를 만들어 실행 | 테스트 |
| **출력 리다이렉트 시 한글·기호에서 UnicodeEncodeError** | **제품 결함** — `ytdl4k -F URL > list.txt` 가 죽는다 |
| POSIX 실행 권한 비트 검사 | 테스트 |
| 스모크 테스트가 stdout=None 에서 죽음 | 빌드 스크립트 |

### ffmpeg 빌드 선정 주의

배포 후보 ffmpeg 은 **왕복 검사**(`scripts/fetch_ffmpeg.py`)를 통과해야 한다.
컨테이너별로 실제 쓰는 코덱 조합으로 파일을 만들고 다시 읽어 본다.

| 컨테이너 | 쓰이는 곳 | PyPI static 7.0.2 |
| --- | --- | --- |
| mp4 (h264+aac) | DASH 병합 — **YouTube 4K 의 기본 경로** | 정상 |
| webm (vp8/9+opus) | VP9/Opus 병합 | 정상 |
| mkv | 혼합 코덱 병합 | 정상 |
| mpegts | HLS·라이브 스트림 | **세그폴트** |

즉 PyPI 폴백 빌드로도 YouTube 4K 다운로드는 문제없지만, 라이브 스트림 지원(P2)을
넣을 때는 다른 빌드가 필요하다. 릴리스 워크플로는 공식 static 빌드를 우선 쓰고
그게 막혔을 때만 PyPI 로 폴백한다.
