# 파일 지도 — 이 저장소에 뭐가 들어 있나

프로그램을 만드는 사람이 아니어도 읽을 수 있게 쓴 문서입니다.
저장소에 있는 파일 **49개**가 각각 무슨 일을 하는지, 왜 그렇게 나뉘어 있는지 설명합니다.

---

## 들어가기 전에 — 왜 파일을 이렇게 잘게 나눴나

프로그램 전체를 파일 하나에 몰아넣어도 동작은 합니다. 다만 두 가지가 곤란해집니다.

**첫째, 고칠 때마다 전부를 다시 확인해야 합니다.** 화면 색깔 하나 바꿨는데 다운로드가
망가졌을 수도 있으니까요. 역할별로 나눠 두면 "화질 고르는 규칙"만 따로 시험할 수 있습니다.

**둘째, 화면 없이는 아무것도 시험할 수 없게 됩니다.** 이 프로그램의 자동 시험 162가지 중
대부분은 창을 띄우지 않고 돕니다. 계산 부분과 화면 부분이 섞여 있으면 불가능한 일입니다.

### 전체 그림

작업장에 비유하면 이렇습니다. 손님(사용자)은 창구만 보지만, 뒤에는 세 층이 더 있습니다.

```
   창구          주소를 받고 결과를 보여 준다        gui/ · cli/
     ↓
   작업 관리     누구 것을 먼저, 몇 개를 동시에       app/
     ↓
   기술자        실제로 받고 합친다                  core/
     ↓
   외부 장비     yt-dlp(주소 해석) · ffmpeg(합치기)
```

> **중요한 규칙 하나**: 위층은 아래층을 알지만, **아래층은 위층을 모릅니다.**
> 기술자는 창구가 있는지조차 모르고, 작업 관리자는 창이 어떻게 생겼는지 모릅니다.
> 덕분에 창구를 통째로 바꿔도(명령줄 → 창 화면) 아래층은 손대지 않았습니다.

## 1. 실제로 일하는 부분 — `ytdl4k/` 폴더 (22개 파일, 약 2,500줄)

### 1-1. 기술자 — `core/` 폴더

프로그램의 알맹이입니다. 화면도 모르고 목록도 모르고, 오직 "이 영상을 어떤 화질로 받아서
어떻게 합칠까"만 생각합니다.

| 파일 | 하는 일 | 이 파일이 없으면 |
| --- | --- | --- |
| **`formats.py`** | **이 프로그램의 심장.** 유튜브가 내놓은 수십 가지 화질 중 무엇을 받을지 정합니다. "4K 이하 최고 화질, 같은 화질이면 60fps, 그다음 화질 좋은 코덱" 같은 규칙이 전부 여기 있습니다 | 무엇을 받을지 정할 수 없습니다 |
| `models.py` | 유튜브에서 온 지저분한 정보를 깔끔한 형태로 정리합니다. `vp09.00.50.08` 같은 암호를 `vp9` 로, HDR 여부를, 파일 크기를 계산해 냅니다 | 나머지 파일들이 유튜브의 사정을 일일이 알아야 합니다 |
| `downloader.py` | 실제로 내려받습니다. 진행률 알림, 취소, 이어받기, 저장 공간 확인, 표지 넣기 판단 | 받을 수 없습니다 |
| `extractor.py` | 주소를 넣으면 영상 정보를 가져옵니다. 실패하면 "로그인이 필요합니다", "지역 제한입니다" 처럼 **사람이 알아들을 말로 바꿔 줍니다** | 오류가 영어 기술 용어 그대로 튀어나옵니다 |
| `merger.py` | 영상 합치는 도구(ffmpeg)를 찾아내고, 합친 결과에 소리가 제대로 들어갔는지 검사합니다 | "화면은 나오는데 소리가 없는 4K 파일" 이 조용히 만들어집니다 |
| `errors.py` | 모든 오류를 **원인 + 사용자에게 보일 말 + 다음에 할 일** 세 쪽으로 정리합니다 | "Error 1" 같은 불친절한 메시지만 남습니다 |
| `__init__.py` | 바깥에서 쓸 것들의 목록. 창구 역할입니다 | |

> **왜 `formats.py` 가 심장인가**: 4K 다운로드의 어려움은 "받는 것" 이 아니라 "고르는 것" 에
> 있습니다. 유튜브는 한 영상에 20~30가지 형식을 내놓고, 그중 1080p 를 넘는 것은 전부
> 소리가 빠져 있습니다. 어떤 영상과 어떤 소리를 짝지어야 하는지 정하는 게 이 파일입니다.
> 인터넷에 연결하지 않고도 시험할 수 있게 만들어 두어서, 유튜브가 바뀌어도 이 규칙의
> 시험은 계속 유효합니다.

### 1-2. 작업 관리 — `app/` 폴더

| 파일 | 하는 일 | 이 파일이 없으면 |
| --- | --- | --- |
| `queue.py` | 여러 영상을 받을 때 순서와 동시 개수를 관리합니다. 하나가 실패해도 나머지는 계속 갑니다 | 한 번에 하나씩만, 그것도 실패하면 전부 멈춥니다 |
| `settings.py` | 저장 위치·화질 같은 설정을 파일에 기록하고 다시 읽습니다. 설정 파일이 깨져 있어도 기본값으로 뜹니다 | 켤 때마다 매번 다시 골라야 합니다 |
| `__init__.py` | 위 둘의 목록 | |

> 이 폴더는 **창 화면에 대해 아무것도 모릅니다.** 일부러 그렇게 만들었습니다. 그래서 화면
> 없이 시험할 수 있고, 나중에 명령줄에서도 같은 큐를 그대로 쓸 수 있습니다.

### 1-3. 창 화면 — `gui/` 폴더

| 파일 | 하는 일 | 이 파일이 없으면 |
| --- | --- | --- |
| `main_window.py` | 창 전체. 주소 입력칸, 화질 선택, 목록, 버튼이 다 여기 있습니다 | 창이 없습니다 |
| `model.py` | 목록 표를 그립니다. 진행률 막대도 여기서 그립니다 | 목록에 아무것도 안 보입니다 |
| `bridge.py` | **14줄짜리 작은 파일이지만 없으면 프로그램이 조용히 망가집니다.** 다운로드는 뒤에서 따로 돌아가는데, 그 결과를 화면에 옮길 때는 반드시 정해진 통로로 넘겨야 합니다 | 화면이 멋대로 깨지거나 멈춥니다 |
| `app.py` | 프로그램을 띄우고, 복사한 주소를 감지합니다 | 창을 띄울 방법이 없습니다 |
| `__init__.py`, `__main__.py` | 실행 통로 | |

> **`bridge.py` 이야기**: 다운로드는 시간이 오래 걸리니 뒤에서 따로 돌립니다. 그런데 화면은
> 한 곳에서만 손대야 한다는 규칙이 있습니다. 이 규칙을 어기면 당장은 잘 되는 것처럼 보이다가
> 어느 날 갑자기 창이 깨집니다. 이 파일이 그 경계를 지킵니다.

### 1-4. 명령줄 — `cli/` 폴더

검은 화면에 명령을 입력해 쓰는 방식입니다. 창 화면보다 먼저 만들었습니다.

| 파일 | 하는 일 |
| --- | --- |
| `main.py` | 입력한 명령을 해석하고, 진행률을 한 줄로 보여 주고, `--self-check` 로 상태를 점검합니다 |
| `__init__.py` | 빈 파일. 폴더를 하나의 묶음으로 표시하는 표지입니다 |

### 1-5. 나머지

| 파일 | 하는 일 |
| --- | --- |
| `__init__.py` | 버전 번호(0.1.0) 하나 |
| `__main__.py` | `python -m ytdl4k` 로 실행할 때 쓰는 입구 |
| `console.py` | **윈도우에서 결과를 파일로 저장하면 프로그램이 죽던 문제**를 막습니다. 윈도우가 한글과 기호를 화면에 띄울 때와 파일에 쓸 때 다르게 처리해서 생긴 일이었습니다 |
| `resources/ffmpeg/.gitkeep` | 빈 표시 파일. 실행 파일을 만들 때 여기에 영상 합치는 도구가 들어옵니다. 도구 자체(80MB)는 저장소에 올리지 않습니다 |

## 2. 시험지 — `tests/` 폴더 (14개 파일, 162가지 시험)

코드를 고칠 때마다 자동으로 돌아가는 시험입니다. **사람이 매번 확인할 수 없는 것들을
기계가 대신 확인합니다.** 실제로 이 시험들이 잡아낸 문제가 여러 건 있습니다.

| 파일 | 무엇을 지키나 |
| --- | --- |
| **`fixtures/formats_4k.json`** | **가짜 유튜브 응답.** 4K·8K·HDR 이 섞인 화질 목록을 미리 적어 둔 것으로, 인터넷 없이 "고르는 규칙" 전부를 시험할 수 있게 해 줍니다 |
| `conftest.py` | 위 가짜 자료를 모든 시험이 함께 쓰도록 준비합니다 |
| `test_formats.py` | 화질·코덱·컨테이너 고르는 규칙 |
| `test_models.py` | 유튜브 정보 해석 |
| `test_extractor.py` | 오류를 사람 말로 바꾸는 규칙 |
| `test_downloader.py` | 내려받기 설정, 진행률, 취소 |
| `test_merger.py` | 합치는 도구 찾기와 결과 검사 |
| `test_thumbnail.py` | 표지 넣기와, 넣을 수 없을 때의 대처 |
| `test_queue.py` | 여러 개 동시 처리, 하나가 실패해도 나머지가 도는지 |
| `test_settings.py` | 설정 저장·복원 |
| `test_cli.py` | 명령줄 동작 |
| `test_gui.py` | 창 화면 동작 (창을 실제로 띄우지 않고 시험합니다) |
| `test_integration_local.py` | **진짜로 받아 봅니다.** 시험용 서버를 띄워 파일을 내려받고 내용이 같은지 확인합니다 |
| `test_fetch_ffmpeg.py` | 합치는 도구를 가져오는 절차 |

> **시험이 실제로 잡아낸 것들**: 부탁하지 않은 HDR 영상이 선택되던 문제(일반 모니터에서
> 색이 바래 보입니다), 갓 켠 컴퓨터에서 진행률 첫 표시가 사라지던 문제, "최고 화질" 설정이
> 껐다 켜면 4K 로 되돌아가던 문제. 셋 다 사람이 눈으로 봐서는 찾기 어려운 것들입니다.

## 3. 포장 공장 — `scripts/`, `.github/` (6개 파일)

소스 코드를 **그냥 실행되는 파일 하나**로 만드는 절차입니다.

| 파일 | 하는 일 |
| --- | --- |
| `scripts/fetch_ffmpeg.py` | 영상 합치는 도구(ffmpeg)를 구해 옵니다. 단순히 받기만 하는 게 아니라 **형식별로 만들어 보고 다시 읽어 보는 검사**를 합니다 |
| `scripts/build.py` | 실행 파일을 만듭니다. 만든 뒤 실제로 실행해서 뜨는지 확인합니다 |
| `scripts/pyi_entry.py` | 실행 파일의 입구(명령줄용) |
| `scripts/pyi_entry_gui.py` | 실행 파일의 입구(창 화면용) |
| `.github/workflows/ci.yml` | 코드를 올릴 때마다 **윈도우와 리눅스에서 자동으로 시험**합니다 |
| `.github/workflows/release.yml` | 세 가지 운영체제용 실행 파일을 자동으로 만듭니다 |

> **왜 ffmpeg 을 검사까지 하나**: 받아 온 도구가 "버전 알려 줘" 에는 멀쩡히 대답하면서
> 특정 형식의 영상을 읽으면 그대로 죽는 경우가 실제로 있었습니다. 그대로 배포했다면
> 사용자가 먼저 겪었을 문제입니다. 그래서 형식마다 만들어 보고 읽어 보는 검사를 넣었습니다.

> **왜 입구 파일이 따로 있나**: 평소 쓰는 입구(`__main__.py`)는 실행 파일로 묶으면 깨집니다.
> 파일 위치를 찾는 방식이 달라지기 때문입니다. 그래서 묶을 때 전용 입구를 따로 둡니다.

## 4. 설명서와 설정 (7개 파일)

| 파일 | 하는 일 |
| --- | --- |
| `README.md` | 첫 화면. 무엇인지, 어디서 받는지, 어떻게 쓰는지 |
| `pyproject.toml` | 프로그램 정보와 필요한 부품 목록. `ytdl4k` 라는 명령으로 실행되게 하는 것도 여기 설정입니다 |
| `.gitignore` | 저장소에 올리지 **않을** 것들의 목록 — 만들어진 실행 파일, 받은 영상, 80MB 짜리 ffmpeg |
| `docs/PLAN.md` | 개발 계획과 일정. **계획과 달라진 결정과 그 이유**도 함께 기록합니다 |
| `docs/REQUIREMENTS.md` | 무엇을 만들 것인가. 중요도(P0/P1/P2)로 나눈 목록 |
| `docs/ARCHITECTURE.md` | 구조 설계. 왜 이렇게 나눴는지 |
| `docs/CODEMAP.md` | 이 문서 |

> **`.gitignore` 가 필요한 이유**: 저장소는 "만드는 재료" 를 보관하는 곳이지 "만들어진 물건" 을
> 두는 곳이 아닙니다. 실행 파일은 재료에서 언제든 다시 만들 수 있으므로 올리지 않습니다.
